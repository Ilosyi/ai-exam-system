## 5. 当前已知问题 / 风险

### 5.1 工程层面

1. `client/src` 中仍存在大量 TS 同名 JS 镜像文件
2. `client/dist` 构建产物仍容易进入版本变更面
3. 前端 chunk 体积偏大
4. 自动化测试覆盖不足

### 5.2 业务层面

1. 编程题还未形成完整闭环
2. 监考能力仍只有基础事件采集
3. 成绩统计与导出尚未实现
4. 权限模型仍主要停留在路由与资源归属层，未形成更细粒度策略

### 5.3 AI 能力层面

1. OpenAI 兼容服务的上游稳定性仍取决于供应商
2. 即使请求超时，供应商侧仍可能已消耗 token
3. 目前已通过超时配置、`/no_think` 和诊断卡片降低排查成本，但还没有做更强的降级与重试策略

## 8. 当前建议的开发节奏

推荐接下来按下面的顺序推进：

1. 先做编程题 MVP
2. 再做监考能力增强
3. 再补成绩分析与导出
4. 最后系统性处理工程质量

原因：

- 主链路功能已经齐了
- 继续补“普通 CRUD”收益下降
- 编程题和监考是当前最明显的功能空白
- 工程治理应放在关键能力补齐后集中推进
